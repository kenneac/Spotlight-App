Spotlight · Convex backend

How the backend fits together.

A code-grounded map of the social feed, profile and follow data, Clerk identity flow, Convex functions, webhook provisioning, and image storage.

7 app tables 16 registered functions 1 HTTP endpoint 0 actions or scheduled jobs
01 · Purpose

Backend overview

Convex supplies the app’s typed function API, reactive database, and managed file storage. Clerk supplies client sign-in and the JWT identity consumed by Convex.

DB

Social app data

The backend stores users, posts, likes, comments, follows, notifications, and bookmarks. Public query and mutation exports provide the client API; one internal mutation provisions a user from a verified Clerk event.

ID

Client identity

The Expo app wraps its tree in ClerkProvider and ConvexProviderWithClerk. Clerk handles Google OAuth sign-in; Convex receives Clerk-issued identity tokens through the provider integration.

IMG

Image lifecycle

The client requests a Convex upload URL, uploads the selected image directly, then submits the returned storage ID with the post. Convex resolves a serving URL and removes the stored file when its post is deleted.

HTTP

Clerk provisioning

A single POST /clerk-convex-webhook endpoint verifies Svix headers and signature. For user.created, it calls internal.users.createUser.

Scope note. The repository has no convex.json or checked-in local .env* file. Deployment URLs, actual environment values, deployment topology, and production settings cannot be determined from this source snapshot.

JWT verification configuration

Identity to application user

getAuthenticatedUser calls ctx.auth.getUserIdentity(), rejects a missing identity, then resolves a users record where clerkId === identity.subject. It rejects an absent record. This code uses subject, not tokenIdentifier.

09 · Handler behavior

Function execution pipeline

Convex does not have a project-defined middleware chain. The order is the handler’s own code, after platform dispatch and any declared argument validation.

Authenticated write example

posts.deletePost

Declared postId validator → resolve authenticated user → load post → explicit owner comparison → delete associated table rows → delete storage object → delete post → update user count.

Read with no auth

comments.getComments

Declared postId validator → query comments by index → fetch user for each comment → return enriched array. No identity or ownership check appears in the handler.

Conditional identity path

posts.getPostsByUser

Optional user ID validator → supplied ID: read user directly; omitted ID: resolve authenticated user → query posts → return array.

Webhook-triggered internal write

http.ts → users.createUser

Read secret → require Svix headers → verify raw body signature → parse and inspect event → validate user ID/email → internal mutation checks for existing Clerk ID → insert if absent.

10 · Integrations

Webhook & external services

Only one incoming webhook is registered. The backend contains no outgoing third-party API call or event scheduler.

POST

/clerk-convex-webhook

HTTP router in convex/http.ts. Accepts POST; reads CLERK_WEBHOOK_SECRET; requires svix-id, svix-signature, and svix-timestamp; verifies the raw body with new Webhook(secret).verify(...). Malformed payloads and signature/header errors return 400; missing secret returns 500.

Handles user.created only. Requires data.id and first email_addresses[].email_address, derives fullname from first/last name, then invokes internal.users.createUser. Other verified event types do not trigger a mutation and receive the normal 200 response.

Environment variable names

Backend reads the first two values; the app provider reads the latter two. Values are intentionally omitted.

11 · Images

File storage

Convex managed storage is used for post images. The image bytes bypass the app server and are uploaded by the client to the generated URL.

01

Request an upload URL

The create screen calls api.posts.generateUploadUrl. The mutation requires a non-null Convex identity and returns ctx.storage.generateUploadUrl().

02

Upload from Expo

The client creates an Expo File from the selected local URI and posts it with expo/fetch, setting the file content type (or image/jpeg fallback). It reads storageId from the response.

03

Persist the reference

The client calls api.posts.createPost({ storageId, caption }). The mutation resolves ctx.storage.getUrl(storageId), stores that URL in posts.imageUrl and the storage ID in posts.storageId, and increments the author’s post count.

04

Delete with the post

posts.deletePost verifies ownership, removes associated rows, invokes ctx.storage.delete(post.storageId), then deletes the post and updates the author’s count.

Serving path: the stored imageUrl is returned with the post and consumed by Expo Image components. No separate file-serving HTTP endpoint is defined in this project.
